# 2. 트리거

플로우당 트리거는 **하나**입니다. 트리거 선택이 잘못되면 뒤의 모든 설계가 흔들립니다.

## 2.1 트리거 동작 방식: 폴링 vs 푸시

| 방식 | 동작 | 예시 | 특징 |
| --- | --- | --- | --- |
| **폴링(Polling)** | 주기적으로 "새 항목 있나?" 조회 | SharePoint 항목 생성, Outlook 메일 수신 | 조회할 때마다 **API 요청을 소모**. 최소 간격은 라이선스에 따라 다름 |
| **푸시(Webhook)** | 서비스가 변경을 알려줌 | Dataverse 행 변경, Teams 특정 이벤트 | 지연이 짧고 요청 소모가 적음 |

폴링 트리거는 **아무 일이 없어도 계속 요청을 씁니다.** 하루 종일 도는 플로우를 여러 개 만들면
요청 한도를 조용히 갉아먹습니다(7장).

## 2.2 주요 트리거

### 되풀이(Recurrence) — 예약 실행

```
간격: 1  빈도: 일
고급 옵션:
  표준 시간대: (UTC+09:00) 서울
  기본 시간: 09:00
  이 날짜에: 월, 화, 수, 목, 금
```

> 표준 시간대를 지정하지 않으면 **UTC 기준**으로 돕니다. 한국 시간 09시로 착각하면 18시에 도는 사고가 납니다.
> 서머타임이 있는 지역을 대상으로 한다면 표준 시간대를 반드시 명시하세요.

### HTTP 요청 수신 시 (When an HTTP request is received)

외부 시스템(예: **VBA**, 사내 서버, 웹훅)이 플로우를 호출하게 만드는 트리거입니다. 프리미엄.

- 저장하면 **HTTP POST URL**이 생성됩니다. 이 URL에는 서명(`sig=`)이 들어 있어 **그 자체가 비밀번호**입니다.
- 요청 본문 JSON 스키마를 넣으면 이후 단계에서 동적 콘텐츠로 필드를 고를 수 있습니다.
- **응답(Response)** 액션이 없으면 즉시 `202 Accepted`를 돌려주고 비동기로 처리합니다.
- 응답 액션이 있으면 동기 응답을 주지만, **약 120초** 안에 끝나야 합니다.

자세한 호출 방법과 VBA 코드는 [11. VBA 연동](11-vba-integration.md)에 있습니다.

### 항목이 만들어지거나 수정되는 경우 (SharePoint)

편리하지만 **함정이 있습니다**: 플로우가 그 항목을 다시 업데이트하면 트리거가 또 걸려 **무한 루프**가 됩니다.
아래 트리거 조건으로 막으세요.

## 2.3 트리거 조건 — 가장 중요한 최적화

트리거 설정(⋯ → **설정** → **트리거 조건**)에 표현식을 넣으면,
**조건에 맞지 않는 이벤트는 실행 자체가 만들어지지 않습니다.**

```
@equals(triggerOutputs()?['body/Status/Value'], '승인요청')
```

`조건(Condition)` 액션과의 차이가 핵심입니다.

| | 트리거 조건 | 조건 액션 |
| --- | --- | --- |
| 판정 시점 | 실행 생성 **전** | 실행 시작 **후** |
| 실행 기록 | 남지 않음 | 남음 (불필요한 기록으로 지저분해짐) |
| API 요청 소모 | 없음 | 소모 |

### 작성 규칙

- 반드시 `@` 로 시작합니다. (`@{...}` 아님)
- 여러 조건은 `@and(...)`, `@or(...)` 로 감쌉니다.
- 값이 없을 수 있는 필드는 `?[...]` 로 접근합니다.
- 트리거 출력 경로는 실행 기록의 트리거 **원시 출력 보기**에서 확인하는 게 가장 정확합니다.

```
@and(
  equals(triggerOutputs()?['body/Status/Value'], '승인요청'),
  not(equals(triggerOutputs()?['body/Editor/Email'], 'flow-bot@contoso.com'))
)
```

두 번째 줄이 **무한 루프 방지** 패턴입니다. 플로우가 쓰는 계정이 수정한 건 무시합니다.

> 표현식을 여러 줄로 써도 되지만, 저장 후 한 줄로 정규화됩니다.
> 트리거 조건은 문법 오류가 있어도 저장이 되고 **아무 이벤트도 안 잡히는** 형태로 실패합니다.
> 조건을 넣은 뒤에는 반드시 실제 이벤트로 한 번 테스트하세요.

## 2.4 분할 개수(Split On)

트리거가 배열을 돌려주는 경우(예: 여러 항목을 한 번에 가져옴), 분할 개수를 켜면
**배열 항목마다 실행이 하나씩** 만들어집니다.

| 설정 | 결과 |
| --- | --- |
| 켬(기본값인 트리거 다수) | 항목 5개 → 실행 5개. 각 실행은 항목 1개만 다룸 |
| 끔 | 항목 5개 → 실행 1개. 안에서 `각각에 적용`으로 반복 |

- 항목별로 독립 처리·독립 재시도가 필요하면 **켬**
- 전체를 하나로 묶어 요약·집계해야 하면 **끔**

> 분할 개수를 끄면 실행 수가 줄어 요청 한도에는 유리하지만, 항목 하나가 실패하면 전체 실행이 실패로 남습니다.

## 2.5 동시성 제어(Concurrency Control)

기본적으로 트리거는 **여러 실행을 동시에** 시작할 수 있습니다.

- **순서를 보장해야 한다면** 동시성 제어를 켜고 최대 병렬도를 `1`로 둡니다.
- 대신 처리량이 급격히 떨어지고, 앞 실행이 밀리면 뒤가 대기열에 쌓입니다.

> ⚠️ **트리거 동시성 제어는 한 번 켜면 다시 끌 수 없습니다.** 플로우를 복사해 새로 만들어야 합니다.
> 켜기 전에 정말 필요한지 확인하세요.

## 2.6 트리거 출력 참조

| 표현식 | 반환값 |
| --- | --- |
| `triggerBody()` | 트리거 출력의 `body` 부분 |
| `triggerOutputs()` | 헤더·상태 코드를 포함한 전체 출력 |
| `triggerOutputs()?['headers']?['x-my-header']` | 특정 요청 헤더 |
| `triggerOutputs()?['body/필드명']` | 트리거 조건에서 쓰는 경로 표기 |

> 트리거 **본문 안**에서는 `triggerBody()?['필드명']` 처럼 대괄호 표기를 씁니다.
> `body/필드명` 슬래시 표기는 주로 트리거 조건에서 씁니다. 둘을 섞으면 `null`이 나옵니다.
