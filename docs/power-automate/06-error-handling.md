# 6. 오류 처리

**기본 동작: 한 액션이 실패하면 이후 액션은 전부 건너뛰고 플로우가 실패합니다.**
알림도, 정리 작업도, 호출자에 대한 응답도 없습니다. 그래서 오류 경로를 직접 만들어야 합니다.

## 6.1 실행 구성(Configure run after)

모든 액션은 "이전 단계가 어떤 상태일 때 실행할지"를 지정할 수 있습니다.

액션의 `⋯` → **실행 구성**:

| 옵션 | 의미 |
| --- | --- |
| 성공한 경우 (is successful) | 기본값 |
| 실패한 경우 (has failed) | 이전 단계가 실패했을 때 → **catch 블록** |
| 건너뛴 경우 (is skipped) | 이전 단계가 실행되지 않았을 때 |
| 시간이 초과된 경우 (has timed out) | 제한 시간 초과 |

여러 개를 동시에 체크하면 **OR** 조건입니다.

> `실패한 경우`를 체크한 액션은, 앞이 성공하면 **건너뜀(Skipped)** 상태가 되고
> 플로우 전체는 성공으로 끝납니다. 이게 catch 패턴의 핵심입니다.

## 6.2 try / catch / finally 패턴

범위(Scope) 3개로 만듭니다. **모든 운영 플로우의 기본 골격으로 쓰세요.**

```
[범위: Try]
   ├ 실제 업무 액션들
   │
[범위: Catch]
   │  실행 구성 = 실패한 경우 ✔ / 시간이 초과된 경우 ✔ / 건너뛴 경우 ✔
   ├ 작성: 오류요약   ← result('Try') 로 실패 원인 추출
   ├ 메일 보내기 / Teams 알림
   ├ (HTTP 트리거라면) 응답 500
   └ 종료: Failed
   │
[범위: Finally]
      실행 구성 = 성공한 경우 ✔ / 실패한 경우 ✔ / 건너뛴 경우 ✔ / 시간이 초과된 경우 ✔
   └ 임시 파일 정리, 잠금 해제, 감사 로그 기록
```

### `result()` 로 실패 원인 뽑기

`result('범위이름')`은 그 범위 안 액션들의 결과 배열을 돌려줍니다.

```
작성 (이름: 실패한_액션들)
@filter(result('Try'), item()?['status'], 'Failed')
```

고급 모드 표현식으로는 이렇게 씁니다.

```
@{
  join(
    select(
      filter(result('Try'), equals(item()?['status'], 'Failed')),
      concat(item()?['name'], ': ', string(item()?['error']?['message']))
    ),
    ' | '
  )
}
```

각 결과 항목의 주요 필드:

| 필드 | 내용 |
| --- | --- |
| `name` | 액션 이름 |
| `status` | `Succeeded` / `Failed` / `Skipped` / `TimedOut` |
| `error.code` | 오류 코드 |
| `error.message` | 오류 메시지 |
| `outputs` | 액션 출력 (`statusCode`, `body` 등) |
| `startTime` / `endTime` | 시각 |

> `result()`는 **직속 자식 액션만** 반환합니다. 범위 안의 중첩 범위 내부까지 자동으로 파고들지 않습니다.
> 중첩이 깊으면 안쪽 범위에도 각각 catch를 두는 편이 정확합니다.

### 알림에 넣을 최소 정보

```
플로우: @{workflow()?['name']}
실행 ID: @{workflow()?['run']?['name']}
시각: @{convertTimeZone(utcNow(), 'UTC', 'Korea Standard Time', 'yyyy-MM-dd HH:mm:ss')}
실패 액션: @{outputs('작성_오류요약')}
입력값: @{string(triggerBody())}
실행 링크: (4.2절의 링크 표현식)
```

**실행 링크는 반드시 넣으세요.** 알림만 보고 원인을 찾으러 헤매는 시간이 사라집니다.

## 6.3 재시도 정책(Retry Policy)

액션 `⋯` → **설정** → **재시도 정책**.
네트워크 오류(`408`, `429`, `5xx`)에 대해 자동 재시도합니다.

| 정책 | 설명 |
| --- | --- |
| 기본값 | 지수 간격, 4회 재시도 |
| 없음 | 재시도 안 함 |
| 고정 간격 | 일정 간격으로 n회 |
| 지수 간격 | 간격을 늘려가며 n회 |

**재시도를 끄거나 줄여야 하는 경우**

- **멱등하지 않은 액션** (결제 요청, 메일 발송, 항목 생성)
  → 같은 작업이 두 번 실행될 수 있습니다. 재시도를 끄고 직접 처리하세요.
- 빠르게 실패해야 하는 동기 응답 경로(HTTP 트리거 + 응답)
  → 기본 재시도가 붙으면 120초 응답 제한을 넘길 수 있습니다.

> `4xx` 오류(400 잘못된 요청, 401 인증 실패, 404 없음)는 **재시도해도 소용없습니다.**
> 요청 자체가 잘못된 것이므로 catch로 보내 원인을 알려야 합니다. (`429`는 예외 — 잠시 후 되므로 재시도 대상)

## 6.4 시간 제한(Timeout)

액션 설정의 **시간 제한**에 ISO 8601 기간을 지정합니다(`PT2M` = 2분).
응답이 없는 외부 시스템 때문에 플로우가 몇 시간씩 매달리는 것을 막습니다.

## 6.5 입력 검증 — 오류를 만들지 않는 게 최선

본 처리 전에 필수값을 확인하고 명확한 메시지로 끝냅니다.

```
[범위: 입력 검증]
  ├ 작성 (누락필드):
  │   @union(
  │     if(empty(triggerBody()?['사번']),   createArray('사번'),   createArray()),
  │     union(
  │       if(empty(triggerBody()?['금액']), createArray('금액'), createArray()),
  │       if(empty(triggerBody()?['구분']), createArray('구분'), createArray())
  │     )
  │   )
  └ 조건: @greater(length(outputs('작성_누락필드')), 0)
        → 예: 응답 400 + 종료(Failed, '필수 항목 누락: ...')
```

`400 잘못된 요청`과 `500 서버 오류`를 구분해서 돌려주면
호출하는 쪽(예: VBA)에서 "내가 잘못 보냈다"와 "서버가 문제다"를 구분할 수 있습니다.

## 6.6 실패를 감지하는 방법

플로우가 실패해도 **아무도 자동으로 알려주지 않습니다.** 아래 중 하나는 반드시 구축하세요.

| 방법 | 설명 |
| --- | --- |
| 플로우 내부 catch | 위의 try/catch. 가장 확실하고 맥락 정보가 풍부함 |
| 소유자 실패 알림 메일 | Power Automate 기본 기능. 하루 단위 요약이라 실시간성이 없음 |
| 감시용 플로우 | 다른 플로우의 실행 기록을 주기적으로 조회해 실패를 집계 (Dataverse `Flow 실행` 또는 관리 커넥터 사용) |
| 공동 소유자 지정 | 담당자 부재 시에도 누군가 볼 수 있게 |

> **개인 계정 알림에만 의존하지 마세요.** 퇴사·휴가 시 알림이 사라집니다.
> 팀 공용 메일 주소나 Teams 채널로 보내세요.
