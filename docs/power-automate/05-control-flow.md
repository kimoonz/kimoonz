# 5. 제어 흐름

## 5.1 조건(Condition)

참/거짓 두 분기로 나눕니다.

```
조건: @{triggerBody()?['금액']}  is greater than  1000000
  → 예: 팀장 승인 요청
  → 아니요: 자동 승인
```

**고급 모드**로 전환하면 표현식을 직접 씁니다. 복잡한 조건은 이쪽이 명확합니다.

```
@and(
  greater(int(triggerBody()?['금액']), 1000000),
  not(empty(triggerBody()?['담당자'])),
  or(
    equals(triggerBody()?['구분'], '구매'),
    equals(triggerBody()?['구분'], '외주')
  )
)
```

> 고급 모드로 바꾼 뒤에는 기본 모드로 되돌릴 수 없는 경우가 있습니다.
> 되돌리려면 조건 액션을 지우고 새로 만들어야 합니다.

> ⚠️ `null`과의 비교는 직관과 다르게 동작합니다. 비어 있을 수 있는 값은
> `empty()` 나 `coalesce()`로 먼저 정규화하세요.

## 5.2 스위치(Switch)

값 하나에 대해 여러 갈래로 나눕니다. 조건 중첩보다 훨씬 읽기 좋습니다.

```
켜기: @{triggerBody()?['상태']}
  case '접수'  → 담당자 배정
  case '진행'  → 진행률 갱신
  case '완료'  → 완료 메일 발송
  기본값       → 예외 로그 기록
```

- **케이스 값에 표현식은 쓸 수 없습니다.** 고정 문자열/숫자만 가능합니다.
- 케이스가 하나도 안 맞으면 **기본값**으로 갑니다. 기본값에 아무것도 없으면 조용히 지나갑니다.
  → 예상 못한 값을 잡으려면 기본값에 로그나 알림을 반드시 넣으세요.

## 5.3 각각에 적용(Apply to each)

배열을 반복합니다.

```
이전 단계에서 출력 선택: @{body('항목_가져오기')?['value']}
  현재 항목 참조: @{items('각각에_적용')?['Title']}
```

### 자동 생성되는 반복 — 성능의 주범

단일 항목 액션에 배열을 넣으면 Power Automate가 **자동으로** `각각에 적용`을 감쌉니다.
의도한 게 아니라면 반복이 배열 크기만큼 API 요청을 씁니다.

배열이지만 실제로는 항상 1건이라면 `first()`로 꺼내 쓰세요.

```
@first(body('항목_가져오기')?['value'])?['Title']
```

### 동시성 제어

설정 → **동시성 제어**를 켜면 병렬도를 지정할 수 있습니다.
기본 병렬 처리 수준은 20이고, 켜면 1~50 범위에서 조정합니다.

| 병렬도 | 언제 |
| --- | --- |
| 1 (순차) | 순서가 중요하거나, 반복 안에서 **변수를 누적**할 때 |
| 20~50 | 항목끼리 독립적이고 처리량이 중요할 때 |

> ⚠️ 병렬도를 올리면 대상 시스템에 순간 부하가 몰려 **429(요청 제한)** 가 납니다.
> SharePoint·SQL 대상이면 10 이하로 두는 편이 안전합니다.

> ⚠️ **반복 안에서 변수를 갱신하면서 병렬로 돌리면 결과가 틀립니다.**
> 누적이 필요하면 병렬도를 1로 하거나, `선택`/`배열 필터링`/`조인`으로 반복 자체를 없애세요(3장).

### 중첩 반복

중첩하면 `item()`이 어느 반복을 가리키는지 모호해집니다.
**반복 액션 이름을 명시**하세요.

```
바깥: items('주문_반복')?['주문번호']
안쪽: items('품목_반복')?['품목명']
```

## 5.4 Do until (~할 때까지)

조건이 참이 될 때까지 반복합니다. 비동기 작업의 완료를 기다릴 때 씁니다.

```
값: @{variables('상태')}   is equal to   완료

제한(고급 옵션):
  개수:     60      ← 최대 반복 횟수
  시간 제한: PT1H    ← 최대 소요 시간 (ISO 8601 기간)
```

**반드시 지킬 것**

1. **루프 안에 `지연(Delay)` 을 넣으세요.** 없으면 순식간에 제한 횟수를 다 쓰고 API 한도를 태웁니다.
2. **탈출 조건을 두 개 두세요** — 성공 조건 + 최대 시도 횟수.
3. 루프가 끝난 뒤 **왜 끝났는지 확인**하세요. 조건 충족인지 제한 도달인지 구분해야 합니다.

```
변수 초기화: 시도횟수 = 0, 완료여부 = false

Do until:  @or(variables('완료여부'), greaterOrEquals(variables('시도횟수'), 30))
  ├ 지연 10초
  ├ HTTP - 상태 조회
  ├ 변수 설정: 완료여부 = @equals(body('HTTP')?['status'], 'done')
  └ 변수 증가: 시도횟수 + 1

조건: @variables('완료여부')
  → 아니요: 종료(Terminate, Failed, '시간 초과: 30회 조회 후에도 완료되지 않음')
```

시간 제한(`PT1H`)은 ISO 8601 기간 형식입니다: `PT30S`(30초), `PT15M`(15분), `PT2H`(2시간), `P1D`(1일).

## 5.5 범위(Scope)

여러 액션을 하나의 블록으로 묶습니다.

- **가독성**: 긴 플로우를 논리 단위로 접어 둘 수 있습니다.
- **오류 처리**: 블록 전체에 대해 try/catch를 구성합니다(6장). 이게 주 용도입니다.

범위 안 액션이 하나라도 실패하면 범위 전체가 실패로 표시됩니다.

## 5.6 병렬 분기(Parallel branch)

액션 사이의 `+` → **병렬 분기 추가**로 여러 갈래를 동시에 실행합니다.

- 서로 독립적인 작업(메일 발송 + 로그 적재 + Teams 알림)을 동시에 처리해 시간을 줄입니다.
- 분기들은 나중에 다시 합쳐집니다. 합류 지점의 **실행 구성**으로 "모두 성공했을 때만" 같은 조건을 겁니다.

> ⚠️ **병렬 분기 안에서 변수를 쓰지 마세요.** 어느 분기가 먼저 쓸지 보장되지 않습니다.
> 분기별 결과는 `작성` 액션에 담고, 합류 후 `outputs('작성_1')` 처럼 참조하세요.

## 5.7 종료(Terminate)

플로우를 즉시 끝냅니다.

| 상태 | 의미 | 용도 |
| --- | --- | --- |
| Succeeded | 성공으로 종료 | 처리할 게 없어 조기 종료 |
| Failed | 실패로 종료 | 오류 코드/메시지를 남김 |
| Cancelled | 취소로 종료 | 사용자가 중단한 경우 |

```
종료
  상태: Failed
  코드: VALIDATION_ERROR
  메시지: @{concat('필수 항목 누락: ', join(variables('누락필드'), ', '))}
```

**Failed로 끝내야 하는 이유**: 실행 기록에서 빨간색으로 남아 모니터링·재실행 대상이 됩니다.
조용히 Succeeded로 끝내면 문제가 있어도 아무도 모릅니다.

> ⚠️ `종료`는 **병렬 분기 안에서 쓸 수 없습니다.** 최상위 또는 조건 분기 안에서만 가능합니다.

## 5.8 구조 설계 요령

**얕고 넓게, 이름을 붙여서.**

```
❌ 조건 안에 조건 안에 조건 (5단 중첩)
✅ 조기 검증 → 종료 / 스위치로 갈래 나누기 / 범위로 묶기
```

권장 골격:

```
1. [범위: 입력 검증]      필수값 확인 → 문제 있으면 종료(Failed)
2. [범위: 데이터 조회]     필요한 데이터 수집
3. [범위: 본 처리]        실제 업무 로직
4. [범위: 오류 처리]      실행 구성 = "실패한 경우" → 알림 + 응답 + 종료
5. [응답/마무리]
```

액션 이름은 만들 때 바로 의미 있게 바꾸세요.
`HTTP`, `작성 3`, `조건 2` 같은 기본 이름이 20개 쌓이면 유지보수가 불가능해지고,
나중에 이름을 바꾸면 그 액션을 참조하던 표현식이 전부 깨집니다.
