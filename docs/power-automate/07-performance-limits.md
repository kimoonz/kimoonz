# 7. 성능과 제한

## 7.1 성능의 원칙

Power Automate에서 느림·실패의 원인은 거의 항상 **API 호출 횟수**입니다.
액션 하나가 곧 요청 하나이고, 반복 안의 액션은 항목 수만큼 요청을 씁니다.

```
항목 1,000건 × 반복 안 액션 3개 = 요청 3,000회
```

## 7.2 최적화 기법 (효과 순)

### 1) 서버에서 걸러 온다 — 가장 효과가 큼

```
❌ 항목 5,000건 전부 가져오기 → 배열 필터링으로 20건 추림
✅ 필터 쿼리 `Status eq '대기'` 로 20건만 가져오기
```

`상위 개수`, `열 제한`도 같이 지정하세요. 페이로드가 작아지면 실행 시간이 눈에 띄게 줄어듭니다.

### 2) 반복을 없앤다

| 하려는 일 | ❌ 느림 | ✅ 빠름 |
| --- | --- | --- |
| 배열 모양 바꾸기 | 각각에 적용 + 배열에 추가 | **선택(Select)** |
| 조건에 맞는 항목만 | 각각에 적용 + 조건 | **배열 필터링(Filter array)** |
| 문자열로 합치기 | 각각에 적용 + 문자열에 추가 | **조인(Join)** |
| 개수 세기 | 각각에 적용 + 변수 증가 | **`length()`** |
| 특정 항목 찾기 | 각각에 적용 + 조건 | **배열 필터링 + `first()`** |
| 표 만들기 | 각각에 적용 + HTML 조립 | **HTML 테이블 만들기** |

`선택`·`배열 필터링`은 **단일 액션**입니다. 항목이 1,000개여도 요청은 1회입니다.
반복으로 만들면 1,000회입니다. 이 차이가 전부입니다.

### 3) 반복이 꼭 필요하면 동시성을 조정한다

`각각에 적용` 설정 → 동시성 제어. 기본 병렬 수준은 20이며 1~50으로 조정합니다.

- 항목끼리 독립적 → 올리면 빨라짐
- 대상 시스템이 `429`를 뱉기 시작 → 낮춰야 함 (SharePoint/SQL은 10 이하 권장)
- **반복 안에서 변수를 누적** → 반드시 1

### 4) 트리거 조건으로 실행 자체를 막는다

2.3절 참고. 필요 없는 실행은 만들지 않는 것이 가장 저렴합니다.

### 5) 불필요한 액션을 지운다

- 디버깅용 `작성`은 운영 전에 정리
- 안 쓰는 변수 초기화 제거
- 같은 데이터를 두 번 조회하고 있지 않은지 확인 (한 번 조회해 `작성`에 담아 재사용)

### 6) 대량 처리는 나눈다

수만 건을 한 실행에서 처리하려 하지 마세요.

- 날짜/구간으로 나눠 **여러 번 실행**
- 항목마다 "처리됨" 플래그를 두고, 매번 미처리 건만 조회
- 정말 대량이라면 Power Automate 대신 Azure Functions / Data Factory 검토

## 7.3 주요 제한값

> ⚠️ 아래 값은 참고용이며 **라이선스·환경·커넥터에 따라 다르고 자주 바뀝니다.**
> 실제 값은 [제한 및 구성 문서](https://learn.microsoft.com/ko-kr/power-automate/limits-and-config)에서 확인하세요.

| 항목 | 대략적인 값 |
| --- | --- |
| 실행 최대 기간 | 30일 |
| 동기 HTTP 응답 제한 | 약 120초 |
| `각각에 적용` 최대 항목 수 | 100,000 (라이선스에 따라 다름) |
| `Do until` 기본 제한 | 60회 / 1시간 |
| 액션 실행 기록 보존 | 28일 |
| 플로우당 액션 수 | 500 (범위 중첩 시 더 낮음) |
| 메시지 크기 | 커넥터별 상이 (대개 수십~100MB) |
| 하루 API 요청 한도 | 라이선스별 상이 |

### 커넥터별 제한(스로틀링)

각 커넥터는 자체 호출 한도가 있습니다. 예를 들어 SharePoint·Office 365 Outlook은
"연결당 N분에 M회" 형태의 제한이 있어, 넘으면 `429 Too Many Requests`가 납니다.

정확한 값은 커넥터 문서의 **제한(Throttling limits)** 섹션에서 확인하세요:
<https://learn.microsoft.com/ko-kr/connectors/>

**`429`가 날 때 대응**

1. 반복의 동시성을 낮춘다
2. 반복 안에 짧은 `지연`을 넣는다
3. 재시도 정책을 지수 간격으로 둔다 (`429`는 재시도가 유효한 오류)
4. 근본적으로는 호출 횟수를 줄인다 (7.2절)

## 7.4 SharePoint 특유의 제한

| 제한 | 값 | 대응 |
| --- | --- | --- |
| 목록 보기 임계값 | 5,000 | 필터·정렬 열을 **인덱싱** |
| `항목 가져오기` 기본 반환 | 100 | 페이지 매김 켜기 + 임계값 지정 |
| 첨부 파일 | 목록당 제한 있음 | 대용량은 문서 라이브러리로 |

목록이 5,000행을 넘고 인덱스가 없으면, 잘 돌던 플로우가 **어느 날 갑자기** 실패합니다.
증상은 "제한 또는 할당량을 초과했습니다" 형태의 오류입니다.

## 7.5 실행 시간 측정

병목을 찾으려면 실행 기록에서 각 액션의 **소요 시간(Duration)** 을 보세요.
반복 액션은 전체 소요 시간이 표시되므로, 항목 수로 나누면 1건당 비용이 나옵니다.

플로우 안에서 직접 재려면:

```
시작: 작성 (이름: 시작시각) = @{utcNow()}
...
끝:   작성 (이름: 소요초) =
      @{div(sub(ticks(utcNow()), ticks(outputs('작성_시작시각'))), 10000000)}
```

(`ticks`는 100나노초 단위이므로 1천만으로 나누면 초입니다.)
