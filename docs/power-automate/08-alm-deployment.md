# 8. 솔루션과 배포(ALM)

## 8.1 왜 솔루션인가

**솔루션 밖(기본 환경)에서 만든 플로우는 다른 환경으로 옮길 수 없습니다.**
개발 환경에서 만들어 놓고 운영으로 옮기려는 순간 막힙니다.

| | 솔루션 밖 | 솔루션 안 |
| --- | --- | --- |
| 환경 간 이동 | 사실상 불가 (수동 재작성) | 내보내기/가져오기 |
| 연결 관리 | 만든 사람 계정에 고정 | **연결 참조**로 환경별 교체 |
| 환경별 설정값 | 하드코딩 | **환경 변수**로 분리 |
| 버전 관리 | 없음 | 압축 해제해 Git에 커밋 가능 |
| 일괄 배포 | 불가 | 여러 구성 요소를 한 번에 |

**결론: 처음부터 솔루션 안에서 만드세요.** 나중에 옮기는 비용이 훨씬 큽니다.

## 8.2 환경 구성

```
개발(Dev) ──내보내기──▶ 테스트(Test) ──내보내기──▶ 운영(Prod)
 비관리 솔루션              관리 솔루션               관리 솔루션
```

| 구분 | 관리(Managed) | 비관리(Unmanaged) |
| --- | --- | --- |
| 편집 | 불가 | 가능 |
| 삭제 | 솔루션 제거 시 구성 요소도 함께 제거 | 구성 요소가 환경에 남음 |
| 용도 | **테스트/운영** | **개발** |

> 운영 환경에 비관리 솔루션을 넣으면 나중에 깔끔하게 제거할 수 없습니다.
> 운영에는 반드시 관리 솔루션으로 배포하세요.

## 8.3 환경 변수(Environment Variables)

환경마다 달라지는 값을 플로우 밖으로 빼냅니다.

| 예시 | 개발 | 운영 |
| --- | --- | --- |
| API 기본 URL | `https://api-dev.example.com` | `https://api.example.com` |
| 알림 수신 주소 | `dev-team@contoso.com` | `ops@contoso.com` |
| SharePoint 사이트 URL | 개발 사이트 | 운영 사이트 |
| 배치 크기 | `10` | `500` |

**만들기**: 솔루션 → 새로 만들기 → 기타 → 환경 변수
데이터 형식은 텍스트/십진수/예-아니요/JSON/데이터 원본/**비밀** 중 선택합니다.

**플로우에서 참조**: 동적 콘텐츠의 *환경 변수* 목록에서 선택합니다.

**값 설정**: 환경 변수는 *정의*(솔루션에 포함)와 *현재 값*(환경에 저장)이 분리됩니다.
관리 솔루션을 가져올 때 대상 환경의 값을 입력하게 됩니다.

> 배포 시 값을 안 넣으면 **기본값**이 쓰입니다. 개발 값이 그대로 운영에 나가는 사고의 원인이므로,
> 운영에 나가면 안 되는 값은 기본값을 아예 비워 두세요.

### 비밀(Secret) 환경 변수

API 키·토큰은 Azure Key Vault에 두고 **비밀 형식 환경 변수**로 참조합니다.
플로우 정의에 값이 남지 않고, 솔루션을 내보내도 비밀이 유출되지 않습니다.

## 8.4 연결 참조(Connection References)

플로우가 "어떤 연결을 쓸지"를 간접 참조로 만듭니다.

```
❌ 연결 참조 없음
   플로우 → 홍길동의 SharePoint 연결 (직접)
   → 홍길동 퇴사 = 플로우 중단

✅ 연결 참조 사용
   플로우 → [연결 참조: SP_운영] → 서비스 계정의 SharePoint 연결
   → 계정이 바뀌면 연결 참조만 교체
```

- 솔루션 안에서 플로우를 만들면 대개 자동으로 생성됩니다.
- 관리 솔루션을 가져올 때 대상 환경의 연결을 지정합니다.
- **서비스 계정(공용 계정)으로 연결을 만드세요.** 개인 계정은 언젠가 반드시 문제가 됩니다.

## 8.5 배포 방법

### 방법 1: 수동 내보내기/가져오기

가장 단순합니다. 소규모 팀에 충분합니다.

1. 개발 환경 → 솔루션 선택 → **내보내기**
2. 버전 지정 → **관리** 선택 → zip 다운로드
3. 운영 환경 → 솔루션 → **가져오기** → zip 업로드
4. 연결 참조·환경 변수 값 지정 → 가져오기

### 방법 2: Power Platform 파이프라인

제품에 내장된 배포 기능입니다. YAML이나 CI/CD 지식 없이 개발 → 테스트 → 운영 승격을 구성합니다.
승인 단계를 넣을 수 있고 배포 이력이 남습니다. 대부분의 팀에는 이 방법이 적절합니다.

### 방법 3: Power Platform CLI + Git

솔루션을 파일로 풀어 소스 관리하고, 파이프라인에서 자동 배포합니다.

```bash
# 인증
pac auth create --environment https://myorg-dev.crm.dynamics.com

# 솔루션 내보내기
pac solution export --name MySolution --path ./out/MySolution.zip --managed false

# zip을 파일 트리로 풀기 (Git 커밋 대상)
pac solution unpack --zipfile ./out/MySolution.zip --folder ./src/MySolution --packagetype Unmanaged

# 다시 zip으로 묶기
pac solution pack --zipfile ./out/MySolution.zip --folder ./src/MySolution --packagetype Managed

# 대상 환경에 가져오기
pac solution import --path ./out/MySolution.zip --activate-plugins
```

`unpack`한 결과에는 각 플로우의 정의가 JSON으로 들어 있어 **diff를 볼 수 있습니다.**
플로우 변경을 코드 리뷰하고 싶다면 이 방식이 유일한 방법입니다.

Azure DevOps나 GitHub Actions에서는 **Power Platform Build Tools**를 쓰면
위 명령들을 태스크로 제공받을 수 있습니다.

## 8.6 배포 후 반드시 확인할 것

가져오기가 성공해도 플로우가 도는 건 아닙니다.

- [ ] **플로우가 켜져 있는가?** 가져온 직후 꺼져 있는 경우가 있습니다.
- [ ] 연결 참조가 올바른 계정으로 연결되었는가?
- [ ] 환경 변수 값이 운영 값으로 들어갔는가? (기본값이 아닌지 확인)
- [ ] 트리거 대상(SharePoint 사이트/목록, 테이블)이 운영 것을 가리키는가?
- [ ] HTTP 트리거라면 **URL이 바뀌었는가?** → 호출하는 쪽(VBA 등)의 설정도 갱신 필요
- [ ] 공동 소유자가 지정되어 있는가?
- [ ] 테스트 실행을 한 번 돌려 봤는가?

> **HTTP 트리거 URL은 환경마다 다릅니다.** 배포할 때마다 호출자 설정을 바꿔야 하므로,
> VBA 같은 클라이언트에는 URL을 **하드코딩하지 말고 설정에서 읽도록** 만드세요(11장).

## 8.7 문서화

플로우는 시간이 지나면 아무도 이유를 모릅니다. 최소한 아래는 남기세요.

- 플로우 **설명란**에 목적·담당자·관련 문서 링크
- 액션 이름을 의미 있게 (`HTTP` → `발주시스템_주문등록_호출`)
- 복잡한 표현식 위에 `작성` 액션으로 주석 대신 중간값 이름 붙이기
- 저장소에 플로우 개요(트리거·주요 단계·연동 대상)를 md로 정리
